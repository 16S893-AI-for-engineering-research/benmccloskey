14 Sept 2026 · Dispatch animation — resolving the open POI→MTF routing bug

Copied the real, unmodified js/dispatch.js into a Node harness that stubs just enough of canvas/window/setInterval/requestAnimationFrame to run the actual production file (not a re-implementation), with two console.log lines inserted only at the two heli.leg = "toBase" assignment sites. Drove it through 3 simulated hours (~2,400+ leg transitions) with a manually advanced clock so timing-dependent behavior wasn't left to chance viewing.

Result: the report was correct, and it wasn't a rendering artifact — it was in the logic. dispatch.js had a deliberate "false alarm" branch: POIs spawned with hasCasualty: false (30% of POIs, per Math.random() < 0.7) sent the helicopter straight from toPOI to toBase, skipping the MTF entirely. The trace showed 707 such direct toPOI→toBase transitions in 3 hours — reproducing the reported bug in the shipped file itself. The prior session's 200k-trial check had only verified that a carrying=true helicopter never skips the MTF, which was true and beside the point; the actual bug was a carrying=false helicopter skipping it, a case that check never asserted against.

Delegated Removed the false-alarm shortcut in advanceHeli(): every completed toPOI leg now routes to the nearest MTF regardless of hasCasualty, and heli.carrying is set from hasCasualty purely for the helicopter's color on that leg, no longer for routing. Updated the header comment in dispatch.js to state the invariant plainly: every pickup goes POI → MTF → BASE.

Checked Re-ran the identical live-trace harness against the patched file (same 3-hour, real-clock run): zero toPOI→toBase transitions, 2,426 toPOI→toMTF completions, 2,425 toMTF→toBase departures (the one-transition gap is a leg still in flight when the trace window closed, not a missed hop). Also loaded the patched index.html in headless Chrome (--headless=new --screenshot) and visually confirmed the canvas, legend, and markers still render with no console errors.

Verification path: real (unmodified except two log lines) dispatch.js executed inside a minimal Node/canvas/timer harness, not a state-machine re-implementation; 3-simulated-hour, real-clock traces before and after the fix (707 violating transitions → 0); headless-Chrome screenshot confirming the live page still renders correctly post-fix. This closes the item left open on 13 Sept — root cause was a routing branch on hasCasualty, not a rendering-layer issue as originally suspected.
